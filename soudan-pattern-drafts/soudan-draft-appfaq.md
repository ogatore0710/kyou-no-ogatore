# 相談室(soudan-kb.js) アプリ使い方FAQ 下書き

調査+下書きのみ。`soudan-kb.js` 本体は未編集。

## 1. 現状カバレッジの確認結果

### soudan-kb.js（相談室）
- `intents[]` は現在 **122件**（L26〜L1659の `{ id: "` をカウント）。すべて「体の悩み・ストレッチの続け方」に関するもの。
  - 身体部位別の悩み（肩こり〜首を鳴らしちゃう）
  - ストレッチの作法系FAQ（`mainichi`毎日やっていい?／`byou`何秒?／`kawaru`いつ柔らかくなる?／`nenrei`何歳からでも?／`kintore`筋トレとどっち?／`ninki`人気の動画／`check`かたさチェック等）
- **アプリの使い方（記録・通知・課金・データ保存など「アプリ運用」に関する質問）は0件**。
  `grep -n "記録\|通知\|おやすみ券\|課金\|無料\|退会\|バックアップ\|ログイン\|アカウント\|ウィジェット" soudan-kb.js` でヒットしたのは無関係な文脈のみ（例: L960「故障ゼロがいちばんの記録更新」、L1955「動画は全部無料」という雑談文脈）で、アプリ機能としての「記録」「無料」等を説明する回答は存在しない。
- `redFlags` / `crisis` / `commonFollowups`（`days` / `asayoru` / `short` / `more`） / `smalltalk` にもアプリ運用FAQは含まれない。

### GuideData.swift（iOSネイティブ・使い方タブ、index.html gstep/FAQと1:1移植）
`ios-native/KyouNoOgatore/KyouNoOgatore/GuideData.swift` の `faqGroups` に29問（4グループ）:
1. **きほんのき**: 料金／通知／動画再生場所／Android対応／オフライン利用／アップデート／古い端末／ホーム画面追加(hidden)
2. **記録・続けるについて**: 保存場所／押し忘れ／おやすみ券／連続切れ／誤タップ／1日2回／通算0リセット(hidden)／機種変更／アイコン削除で記録消失(hidden)／家族共有
3. **きょうの1本・相談室**: 痛かったら／動画の選定基準／相談室の中身（AI不使用・外部送信なし）／2週間プランの解約／リクエスト方法
4. **見ため・その他**: 文字サイズ／ダークモード／じまんカード／カード図鑑／レアカード／せんぱいの声／とどくメーター／使い方の再確認

`index.html` の gstep（使い方タブ本文）には上記に加えて、FAQには無い運用情報として: かたさチェック30秒→タイプ別おすすめ、オガトレ通信（尾形さんの一言・写真・ラジオ）、記録カードの画像保存＝バックアップ、ゴールドカード（節目デザイン）、サボっても「おかえりなさい」から再開、30秒ショート動画、カレンダー印、再生リストタブ、続ける設定（リマインダー・画面のみため）などがある。

→ **これらアプリ運用の情報は、相談室では一切拾えない状態**。ユーザーが相談室のチャット欄に「記録が消えた」「おやすみ券って何」等を打っても、既存intentのkwにヒットせず、汎用のフォールバック（該当なし）になっていると推測される（fallback文言はエンジン側index.html管轄のため今回未確認）。

## 2. 想定される追加が必要な理由・ユーザー例の位置づけ

ユーザー指定の例（「どのくらいの期間で効果出る？」「毎日やらなきゃダメ？」「他の人と比べてどう？」「アプリは無料？」）はいずれも、既存の身体系intent（`kawaru`いつ柔らかくなる?／`mainichi`毎日やっていい?）とは**別の切り口（アプリ運用・継続のモチベーション面）**として書き分けた。
- `kawaru`は「ストレッチで体が変わる期間」の話、今回の`kikanai_app`は「記録・カード等アプリ側の"証拠"でどう実感するか」の話。
- `mainichi`は「毎日ストレッチして体に負担はないか」の話、今回の`mainichigo_app`は「アプリを毎日開けない日があっても続いたことになるか（おやすみ券・サボり文化）」の話。
両者は表面のkwが被る可能性があるため、実装時はkw先頭寄り優先ルール（設計§4-4）に沿った調整が必要（下書き段階では未調整）。

## 3. スキーマに関する提案（要すり合わせ）

既存`intents[]`の契約は `videos:[...1〜3本]` が必須（コメントL6-9）。しかしアプリ運用系の質問には対応する解説動画が存在しないものが大半。
選択肢:
- (a) `commonFollowups`と同様の `mode:"text"` 方式で、動画なしの新カテゴリ `appFaq[]` を新設する（回答のみ、chipから直接呼べる／他intentのfollowupsからも参照できる）。
- (b) 既存`intents[]`に無理に混ぜず、videos必須ルールの例外扱いとして`intents[]`内に`videos:[]`許容の特例を設ける。
(a)の方が既存契約を壊さず、GuideData.swift/index.htmlのFAQと構造的にも対応しやすいため推奨（本人判断待ち）。
下記の下書きは (a) `appFaq[]` 想定のフィールド `{ id, chip, kw, empathy, answer, followups }` で統一。`videos`・`keizoku`は付けていない（案(b)を採る場合は`videos:[]`空配列を許容する運用にする想定）。

## 5. 補足・懸念点（実装時の要検討事項）

1. **kw重複チェック未実施**: `qa.js`のkw重複警告ロジックは走らせていない。特に `hozon`/`kishuhenkou`/`tsuusan0` あたりは既存の腰痛系「記録」等の一般語と被らないか要確認（今回grep調査では実害ヒットなし）。
2. **既存stretch系intentとの意味の切り分け**: 上記I群（`kikanai_app`, `mainichiyaranakya_app`）は、既存の`kikanai`（効いてる気がしない）・`mainichi`（毎日やっていい?）とidも文面も意図的に分けたが、実チャットでどちらに倒すかはエンジン側のマッチング優先度と本人判断が必要。同一chipで統合する案もあり得る。
3. **videos必須契約との整合**: 本書§3の通り、案(a) `appFaq[]` の新設が必要。既存`intents[]`にそのまま追加する場合は`videos:[]`許容のルール変更が要る。
4. **本人検収**: 数字（おやすみ券3枚/月、節目日数等）はGuideData.swift/index.htmlの現行仕様をそのまま転記したが、仕様変更時は両ファイルとの同期が必要。
5. **今回未着手**: `safety`相当のフラグは設けていない（アプリ運用系は基本safety:false相当と判断）。既存`redFlags`/`crisis`との衝突（例:「消えたい」等)は無いことを目視確認済み。
